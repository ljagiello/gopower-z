KM003C firmware analysis

This page covers static analysis of every KM003C application image on ChargerLAB's official Google Drive: 21 packages, 1.7.9 through 2.0.7. Version 1.9.5, the version the user's meter reports, was analysed in depth. 1.9.7, 1.9.9 and the whole 2.0.x line were analysed for the questions that differ between versions. The 2.0.0 build that ships with the Windows app 3.0.0 was also checked. Nothing was sent to a meter and nothing was flashed. All addresses are runtime flash addresses, with the image loaded at 0x00004000. Function names are Ghidra's FUN_xxxxxxxx unless noted.

1. Findings for the CLI

  • Decryption: the method is from okhsunrog/km003c-rs FIRMWARE.md @ c063388, and I verified it independently.
    • The container is a Qt QDataStream: ten QStrings, then one QByteArray of ciphertext.
    • The cipher is AES-128-ECB with key 0, Lh2yfB7n6X7d9a5Z.
    • All 21 Drive packages decrypt to a valid Cortex-M image (base 0x4000, reset vector 0x4295) whose CRC-32 matches the header.
    • Seven packages carry stale bytes after the ciphertext; ignore them.
  • The meter's firmware is not byte-identical to the Drive 1.9.5. The meter's app info block (captured MemoryRead of 0x4420) says 1.9.5, 2025.1.7, 451,748 bytes, stored CRC DD9AD21D. The Drive 1.9.5 is 2025.1.6, also 451,748 bytes, CRC 3F85AC89. Patching only the date string does not reproduce the meter's CRC. Every finding below comes from the Drive 1.9.5 and agrees with the captured 1.9.5 frames.
  • ADC tail on 1.9.5 (same in 1.9.7, 1.9.9 and the Windows-app 2.0.0):
    • 0x24 is an i16 second-temperature slot. Its only writer stores 0x8000, meaning "invalid".
    • 0x26 is the CC2 50-sample average in mV, with the low 2 bits overwritten by the sample-rate index. Your 0x1A = rate 2 = 50 SPS, CC2 24–27 mV.
    • 0x28 and 0x2A are the D+ and D− 50-sample averages in mV.
    From 2.0.1 (both 2026.4 builds) through 2.0.7 the tail changed:
    • 0x26 is the rate only.
    • 0x27 is the accelerometer status and orientation.
    • 0x28 is the PD-reported battery charge in per-mille, or 0.
    • 0x2A is 0xFF.
    Rate index: 0 = 2 SPS, 1 = 10, 2 = 50, 3 = 1000 SPS.
  • IBUS sign (1.9.5 and 2.0.7): the firmware passes the INA229 CURRENT register sign through unchanged. It calibrates positive and negative currents with separate gain tables. It does not decide which physical direction is positive; that takes a bench test.
  • Protocol shown on screen: no GetData attribute carries it.
    • The 1.9.5 dashboard label is a function of (VBUS mV, IBUS mA, D+ mV, D− mV). D+ and D− are exactly payload 0x28/0x2A on 1.9.x. The function is reproduced in §10 so the CLI can compute it.
    • PD details (PD3.0/3.1, PPS/QC4, AVS, Apple/OPPO/Xiaomi VIDs) come from PD messages, which the CLI receives through attribute 0x10.
    • The passively detected proprietary protocol state lives only in RAM.
  • Unauthenticated GetData: on 1.9.5 it is masked with 0x19, which leaves ADC 0x01, settings 0x08 and PD 0x10. AdcQueue, the PD and QC traces and the log list need auth level 1. On 1.9.x that only means echoing the MCU UID under key 3, and it has no other side effect. From 2.0.1 the mask is 0x7F.
  • MemoryRead (0x44) needs Connect but no auth. I checked the dispatcher on 1.9.5, 1.9.9 and 2.0.7; the gate itself is identical in every image from 1.9.5 to 2.0.7. It requires magic 0xFFFFFFFF, size < 0x3D0901 and address < 0x983D0901, with no whitelist. The reply is AES-ECB(key 0) in 2,544-byte chunks. On 2.0.5 a reply that ends in a short chunk sends that last chunk unencrypted while the header flag says plaintext (FIRMWARE.md).
  • Dangerous commands:
    • vendor bulk interface: 0x04 reset, 0x09 DFU, 0x48 settings batch (no auth: persistent settings, reboot, factory reset), 0x4A NOR write and erase (auth ≥ 1), 0x4D calibration (auth 2);
    • CDC virtual serial port: 0x0A settings batch with no auth;
    • CDC text "protocol trigger" mode (pdm open, entry pd, qc 20V, pd req=, ...): makes the attached charger raise VBUS.
    The HID interface answers only GetData.
  • Session on 1.9.5: the first Connect sets a 5 s receive timeout. A second Connect while connected raises it to 120 s. On timeout the firmware resets auth and sends an unsolicited 0x03. GetData works without Connect.

3. Decryption

key   = "Lh2yfB7n6X7d9a5Z"        (protocol key 0, also the MemoryRead key)
plain = AES-128-ECB-Decrypt(key, QByteArray)[:int(QString[7])]
check = crc32(plain with bytes 0x428..0x42F set to 0xFF) == int(QString[6], 16)   # zlib CRC-32
image = flash 0x00004000; padding after 'size' is 0xFF (a full extra block when size % 16 == 0)
  • Source: km003c-rs FIRMWARE.md (§ Package validation). It also documents the bytes the bootloader rewrites at 0x428..0x42F and the 0x4000 base. The bootloader size limit 0x6FFFE was not re-checked here.
  • Independent evidence of ECB before trying a key: identical 16-byte ciphertext blocks repeat within each file, for example 2752eb11…aece 28 times in 2.0.7. Blocks are shared across versions and models; KM002C 2.0.0 and MI2 2.0.0 are identical in 25,299 of 25,302 blocks. The same key also decrypts KM002C, KM002C Lite and MI2.
  • Verification: all 21 Drive packages and the four Windows-app 3.0.0 packages decrypt to SP in SRAM, Reset_Handler = 0x00004295, the app info block at 0x4420 (0x00004000, "KM003C", version, date) matching the header, and a matching CRC-32. The MemoryRead handler addresses that FIRMWARE.md lists for 1.9.9, 2.0.5, 2.0.6 and 2.0.7 (0x46CAC, 0x45514, 0x45524, 0x455BC) are exactly where Ghidra finds them in my images, which confirms the base.
  • Host side: per FIRMWARE.md, the updater sends the original ciphertext and the bootloader decrypts it. CRC-32 is not a signature, so the CLI must never contain an update path.

5. The meter's 1.9.5 vs the Drive 1.9.5

The repository fixture km003c/testdata/fw1.9.5/bulk_W6_2_plain.hex is a MemoryRead of 0x4420 captured from the user's meter. It decodes to:

00 40 00 00  ff ff ff ff  a4 e4 06 00  1d d2 9a dd  "KM003C"  "1.9.5"  "2025.1.7"  "1"
base 0x4000  (unused)     size 451748  CRC DD9AD21D  (written by the bootloader after flashing)

The Drive 1.9.5 has the same size, but its date is 2025.1.6 and its CRC is 3F85AC89. Writing "2025.1.7" into the Drive image and recomputing gives 5097DFBD, not DD9AD21D, so the meter runs a different build of the same size. The bootloader block at 0x0420 on the meter reads "KM003C", "2.2", "2024.9.23" (bulk_W6_1_plain.hex). Nothing visible in the captures contradicts the Drive 1.9.5 analysis:

  • ADC tail 00 80 1a 00 56 00 5a 00;
  • PD preamble u32 tick, u16 vbus_mV, i16 ibus_mA, u16 cc1, u16 cc2;
  • a 180-byte settings block;
  • MemoryRead confirmation byte 2 = 0x01;
  • GetData answered on bulk, HID and CDC alike.

A read-only MemoryRead of the meter's application flash (0x4000..0x72CA4, about 450 KB) compared against the decrypted Drive 1.9.5 (plaintext sha256 22281fde…443d) would settle it. That is a decision for whoever owns the meter.

6. USB command dispatch per interface (1.9.5)

The 1.9.5 USB task is at 0x0001EDD4. It waits for an event, with the session timeout as the wait time, and serves three inputs. The table shows what each interface accepts:

The OUT endpoint-to-buffer mapping comes from the receive-complete callback FUN_00051ee8: EP 1 → bulk, EP 2 → CDC, EP 5 → HID. In 1.9.5 the CDC branch has no binary 0x02 handler, so such a frame reaches the text parser and is ignored there. 2.0.x added CDC 0x02/0x03 start/stop streaming. The repository's guard.go says CDC 0x02 starts a push stream; that matches 2.0.x, not this 1.9.5 code path.

The bulk dispatcher, FUN_00052514 in 1.9.5, is identical to FUN_00052af0 in 1.9.9. If the connected bit (0x20003CD6 bit 2) is clear, it sets auth to 0 and accepts only 0x0C and 0x02; everything else gets Reject 0x06.

The bulk session deadline is 5 s after the last command, checked when the 10 s receive wait expires.

8. ADC payload and the 0x24–0x2B tail

The payload is a memcpy of the first 44 bytes of the ADC state struct, followed by overrides. The struct is at 0x20002560 on 1.9.5, 1.9.7 and 1.9.9 (accessor FUN_000180ac on 1.9.5) and at 0x1FFFACF0 on 2.0.7. Read with the old layout, a 2.0.1+ meter shows an absurd CC2 average. The 61.441 V reported after a test flash to 2.0.7 is 0xF001: rate 1 (the boot default), accelerometer OK, orientation 0xF (flat). Pick the layout by firmware version: ≤ 2.0.0 old, ≥ 2.0.1 new. The rate, p[0x26] & 3, is valid in both. On 2.0.1+ read D+/D− from 0x1E/0x20 (0.1 mV).

Rate index: the per-rate SPS table ({2, 10, 50, 1000}; 1.9.9 0x55DF8, 2.0.7 0x558E6) matches the UI strings "2SPS", "10SPS", "50SPS" and "1KSPS". AdcQueue line voltages come from struct offset 0x1A + 10×rate:

  • rate 0: 0.1 mV, averaged;
  • rate 1: mV, 50-sample average;
  • rates 2 and 3: instantaneous mV.

That is why the queue units change with rate.

9. IBUS sign

  • INA229 read (1.9.5 FUN_00006e6e, 2.0.7 FUN_00006d78): reads register 7 (CURRENT, 20-bit two's complement) and sign-extends it. It switches ADCRANGE near full scale and rescales by 4. It returns the value without negation.
  • Calibration (1.9.5 FUN_00017e20, 2.0.7 FUN_00017b1c): ibus_uA = gain[k]×(raw − offset)/1e6, sign kept. k picks one of 10 gains: five positive ranges with breakpoints at 2.1, 4.1, 6.1 and 8.2 A, and the mirrored negative ranges. Settings op 0x0D writes the negative gains.
  • UI: prints the signed value ("%5.3fV %6.3fA %0.1fW"). There is no direction text or arrow logic.

So the meter measures both directions symmetrically and the firmware defines no physical convention. Which way is positive depends on how the shunt is wired. The official "new ADC" PDF (negative = receptacle → plug) and the km003c-rs comments (positive = female → male, which is the same thing stated the other way) conflict on paper. A bench test with a known load direction settles it. Until then the CLI should report the raw sign.

10. Fast-charge protocol labels

No GetData attribute carries the dashboard's protocol text or the engine's detected-protocol state. The engine object is at 0x200056B0 on 1.9.5 (FUN_0004f8c6) and 0x1FFFC140 on 2.0.7. Reading it needs a version-specific RAM MemoryRead, which is not recommended. What the CLI can do instead:

Dashboard voltage label, 1.9.5 (FUN_0001fb44, called at 0x0004b476 with the ADC struct)

Inputs:

  • v = VBUS mV (struct 0x66; use payload vbus_uV/1000);
  • i = IBUS mA as u16 (struct 0x68; negative currents compare as large);
  • dp, dm = D+/D− 50-sample averages in mV (payload 0x28/0x2A).

This is a branch-by-branch translation:

line1(v, i, dp, dm):
  if v < 3300                                   -> "[ N/A ]"
  if dp > 2800:
    if dm > 2800:
      if v >= 19001                             -> "QC2.0 20V"
      if v > 7000 && i > 1000                   -> "VFCP | UFCS"
      return v < 5500 ? "DCP 1.5A" : "[ N/A ]"
    if 451 <= dm <= 1099: return v > 8500 ? "QC2.0 9V" : "VOOC"
    return v > 8500 ? "SVOOC" : "[ N/A ]"
  if 2501 <= dp <= 2800: return (v < 5500 && 2501 <= dm <= 2899) ? "Apple 2.4A" : "[ N/A ]"
  if 1101 <= dp <= 1300: return (v < 5500 && 1101 <= dm <= 1299) ? "Samsung 2.0A" : "[ N/A ]"
  if 501 <= dp <= 1000:
    if dm > 2800                                -> "QC3.0 | QC3+"
    if 501 <= dm <= 699:
      if 10501 <= v <= 12499                    -> "QC2.0 12V"
      return 4501 <= v <= 5499 ? "DCP 1.5A" : "[ N/A ]"
    if dm < 200:
      if i >= 2001                              -> "QC2.0 | SCP"
      if 8501 <= v <= 12499                     -> "FCP | AFC"
      return 4501 <= v <= 5499 ? "QC2.0 5V" : "[ N/A ]"
  return "[ N/A ]"

line2(v, i, dp, dm):
  if v < 3300                                   -> "[ N/A ]"
  if 8501 <= v <= 9999  && 1100<=dp<=1699 && 1100<=dm<=1699  -> "SFCP 9V"
  if 10000 <= v <= 12499 && 2100<=dp<=2699 && 2100<=dm<=2699 -> "SFCP 12V"
  if v >= 12500 && dp < 700                     -> "FCP | SCP"
  if i <= 2000:
    alt = "[ N/A ]"
    if |dp - dm| < 100:
      if 4501 <= v <= 5499: alt = "DCP 1.5A"
      elif v < 19500 && dp > 3000: alt = "QC2.0 20V Err"
    return (501 <= dp <= 699 && dm < 300) ? "FCP | SCP | AFC" : alt
  if dp > 2900: return v >= 7001 ? "SVOOC" : (v < 5500 ? "VOOC" : "[ N/A ]")
  return "[ N/A ]"

The function first checks whether the engine reports an identified proprietary session (engine +0xD == 0x13). If so, it shows VOOC/SVOOC, VFCP %d.%dW or UFCS %d.%dW from engine state instead of the labels above.

2.0.7 rewrote this function (FUN_000213c8 / FUN_00022098 / FUN_00021bd4). The 2.0.7 version:

  • drops the current input;
  • adds a bare "DCP" label and "QC2.0 12V Error";
  • shows AFC/FCP/SCP/UFCS/VFCP/TFCP/VOOC from an explicit protocol code (engine +0x234).

Use the function that matches the meter's firmware.

PD label (1.9.5 FUN_0002768c; 2.0.7 FUN_00025590)

The label is the PD revision ("PD3.0", or "PD3.1" with "EPR"; 2.0.x adds "PD3.2") plus suffixes:

  • PPS,QC4 or PPS,QC4+ (2.0.x adds PPS,QC5) when an APDO is present, or AVS when the APDO type bits say so;
  • Apple when a VID stored in the PD object is 0x05AC;
  • SVOOC,%dW for 0x22D9 (OPPO) and XIAOMI,%dW for 0x2717.

All of these come from PD traffic, which the CLI sees with PdEnable(1) and attribute 0x10. I did not trace which message fills the VID field; Discover Identity or Source_Capabilities_Extended are the candidates.

11. MemoryRead (0x44) validation

/* 1.9.5: dispatcher case 0x44 + FUN_000468d4.  Identical logic in every analysed version. */
req = (hdr bit16) ? AES-ECB-Decrypt(key0, payload) : payload      // {u32 addr, u32 size, u32 magic, u32 tag}
if (addr - 0x03000C00) < 0x180:                                   // OTP calibration window
    p = first 64-byte record from 0x03000C00 whose first word is 0xFFFFFFFF (max 0x03000D80)
    if p > 0x03000D40: addr = 0x03000D80
if magic == 0xFFFFFFFF && size < 0x3D0901 && addr < 0x983D0901:
    send {0xC4, id, 0x01, 0x01} + {addr, size, 0xFFFFFFFF, tag}     // 20 bytes; byte 2 bit 0 = encrypted
    for each 0x9F0-byte chunk (last rounded up to 16): send AES-ECB-Encrypt(key0, mem)   // raw, no header
else: send Reject {0x06, id}
  • The only requirement is the connected state; there is no auth check. There is no lower bound and no whitelist: flash, bootloader, OTP, SRAM, peripheral registers and the XIP window are all readable. Reading FIFO or clear-on-read registers changes peripheral state.
  • The copy loop (FUN_00005090 on 1.9.5) dereferences the address directly, so an unmapped address raises a bus fault. km003c-protocol-research saw a NOT_READABLE (0x27) reply for one such address on 1.9.9, and the repository's guard notes report crashes. Either way, whitelist.
  • Large sizes, up to about 3.8 MB, keep the USB task busy.
  • The tail is padded to 16 bytes.
  • 0x4B applies the same check to 0x98000000 + addr.
  • 2.0.5 sets the confirmation flag to 0 and sends its final short chunk unencrypted. FIRMWARE.md documents this; its library limits requests to 2,528 bytes to avoid it. The version table in §4 confirms the flag per image.
CLI policy: allow only flash 0x0000–0x7FFFF, OTP 0x03000C00–0x03000FFF, SRAM and the 12-byte UID at 0x40010450. Keep each request ≤ 2,528 bytes and never touch other peripheral space. Useful fixed reads: 0x0420 (bootloader info) and 0x4420 (app model, version, date, installed size and CRC).

12. State-changing commands

A read-only CLI must never send these:
  • 0x04 and 0x09;
  • 0x48 and 0x4D (every op changes state);
  • 0x4A;
  • level-2 auth;
  • CDC 0x0A;
  • any CDC text line.
Reboots also interrupt offline logging. Level-1 auth on 1.9.x is side-effect-free. Start/StopGraph (0x0E/0x0F) changes the live sample rate, which also shows on screen, but is not persisted.

Settings-batch operations (1.9.5 FUN_00046a1c; identical in 2.0.7 FUN_00045704)

Format: [op:15 | next:1 | rsv:6 | size:10] + payload, chained while next is set. The handler is reachable from bulk 0x48 (no auth), bulk 0x4D (auth 2) and CDC 0x0A (no auth).

The OTP calibration record that level-2 auth compares against is itself readable through 0x44. Level 2, and with it calibration writes, is therefore reachable by any host.

CDC text mode: "Protocol Trigger by Virtual Serial Port"

On the CDC port, any frame that is not a 0x0C or 0x0A header goes to the text parser (1.9.5 FUN_00042df2, 2.0.7 FUN_00040718). ChargerLAB's own document, "KM003C/002C Protocol Trigger by Virtual Serial Port (Instructions)", published on their Google Drive next to the firmware, lists the commands:

  • session: pdm open / pdm close, pdm set type=,em= (eMarker simulation up to 50 V 5 A EPR), reset;
  • protocol entry: entry pd|ufcs|qc|fcp|scp|afc|vfcp|sfcp;
  • fixed voltages: qc 5V|9V|12V|20V, fcp|afc|sfcp ?V;
  • stepped QC3: qc3 volt=3600..20000, qc3 inc= / dec=;
  • variable voltage and current: scp volt=,cur=, vfcp volt=,cur=, ufcs req=,volt=,cur=, pd req=,volt=,cur=;
  • raw PD: pd pdo, pd cmd=, pd data= (raw PD messages).

The firmware parser also knows debug, list, ver, info, hrst (hard reset), drp, tfcp, apple and bc.

These commands make the meter act as a decoy sink and negotiate higher voltages, up to 20 V, or 48–50 V with EPR, onto whatever is connected on the output side.

15. Reproduction

No firmware, decrypted or encrypted, is stored in this repository. The inputs are the official .mencrypt packages from ChargerLAB's Google Drive and the four packages bundled with the Windows app 3.0.0, identified below by SHA-256.

  1. Decrypt. A short Python decryption script (pycryptodome) parses the QDataStream header, AES-128-ECB-decrypts the QByteArray with key 0 and truncates to the declared size. It checks the CRC-32 with 0x428..0x42F set to 0xFF, the vector table and the app info block at 0x4420. It then prints the table in §4.
  2. Analyse. Ghidra 12.2 headless with -processor ARM:LE:32:Cortex -loader BinaryLoader -loader-baseAddr 0x4000. A pre-script adds the HC32F460 memory map (SRAMH, SRAM, retention SRAM, OTP, peripherals, QSPI XIP and registers) and seeds functions from the 160-entry vector table. A post-script decompiles every function. The never-returning RTOS tasks have no prologue, so I created them by hand at the addresses in §13. ECB was fingerprinted by counting repeated and shared 16-byte ciphertext blocks.
  3. Per-version ADC check. In each decompiled image, find the GetData builder: the function that copies 0x2C bytes with extended header 0x8001/0xB00. Record the level-0 mask and the tail overrides, find every writer of ADC struct +0x4C, and read the per-rate SPS table that the rate setter indexes.
