powerz CLI reference

Read-only command-line client for the ChargerLAB POWER-Z KM003C (USB 5fc9:0063). Built for humans at a terminal and for AI agents and scripts: JSON on stdout, structured errors, stable exit codes, and a self-describing powerz schema.

1. Build and connect

powerz talks to the meter's vendor USB interface through libusb (cgo).

# macOS
brew install libusb pkgconf
# Debian/Ubuntu
sudo apt install libusb-1.0-0-dev pkg-config

go build -o powerz ./cmd/powerz

Connect the meter's USB-C port marked HID to the computer. The device under test goes between the meter's male and female USB-C ports. On macOS no driver or root is needed. On Linux, the in-kernel powerz hwmon driver owns the interface; powerz detaches it while running. Grant access with a udev rule for 5fc9:0063 or you get exit code 6.

2. Quick start

powerz                       # dashboard on a terminal, one JSON reading when piped
powerz read                  # one snapshot
powerz measure -duration 10s # min/mean/max, energy, charge, PD contract
powerz info                  # model, firmware, serial, settings
powerz pd -duration 30s      # decoded USB-PD traffic
powerz log -duration 1m -interval 500ms -format csv > run.csv
powerz schema                # everything below, as JSON

3. Agent contract

  • JSON whenever stdout is not a terminal. Force it with -json or force text with -text. Every object carries schema_version (currently 1).
  • stdout is data only. Diagnostics, traces and errors go to stderr.
  • Units are in field names: _v volts, _a amperes, _w watts, _wh watt-hours, _mah milliamp-hours, _c °C, _s seconds, _ms milliseconds.
  • Errors are one JSON line on stderr with a stable code, a retryable flag and a hint.
  • Every command can be bounded. read, measure, info, devices and schema terminate on their own. log and pd take -duration or -n, and automation should always pass one.
  • One process per meter. The USB interface is exclusive. A concurrent call fails with busy (exit 4, retryable) unless you pass -wait 10s, which queues behind the other process.
  • Common flags work anywhere, before or after the command: -json -text -serial S -timeout D -wait D -trace.
  • Interpretations are separated from measurements. Fields under inferred are computed by powerz, not reported by the meter.

5. Output fields

FieldMeaning
vbus_v, ibus_a, power_wInstantaneous bus voltage, current (signed) and their product. Resolution 1 µV / 1 µA.
vbus_avg_v, ibus_avg_a, power_avg_wThe meter's own smoothed averages, updated about once per second.
temp_cMeter temperature; null when the meter flags it invalid (e.g. at 1000 SPS).
cc1_v, cc2_vType-C configuration channel voltages.
dp_v, dm_vUSB D+ / D− voltages (used by BC1.2, Apple, QC, etc. signalling).
cc2_avg_v, dp_avg_v, dm_avg_vThe meter's averages of CC2, D+ and D−. Only firmware up to 2.0.0 reports them; on newer firmware they are null. Verified on firmware 1.9.5.
firmware_versionThe meter's application firmware. It is read once per invocation and selects how the firmware-dependent fields are decoded.
sample_rate_spsThe sample rate configured on the meter: 2, 10, 50 or 1000.
temp2_cThe second (reserved, external) temperature channel; normally null.
sink_battery_percentThe sink's battery level as learned by the meter from USB-PD traffic (newer firmware only); otherwise null.
inferred.dashboard_label, inferred.dashboard_label_2The meter's own D+/D− protocol labels (DCP, Apple 2.4A, QC2.0 9V, FCP | AFC, SFCP 9V, [ N/A ], …). powerz recomputes them from VBUS, D+ and D− with the algorithm ported from the meter firmware, so they match the screen.
vdd_vThe meter's internal supply voltage.
inferred.ccpowerz's reading of the CC levels (Default USB / 1.5 A / 3.0 A Type-C advertisement). Inference.
raw.*Uncalibrated averages and the ADC tail bytes, for debugging.
energy_wh, charge_mah(measure) Signed integrals of power and current over the measurement.
pd.source_capabilities(measure) PDOs most recently advertised by the charger.
pd.contract(measure) The sink request acknowledged by PS_RDY, i.e. the negotiated contract, or null.

The complete, authoritative list is in powerz schema.

7. Agent recipes

How much power does the attached device draw?

powerz measure -duration 30s -wait 10s -json
# use .power_w.mean, .power_w.max, .energy_wh, .vbus_v.mean, .ibus_a.mean

What does this charger offer, and what did the device negotiate?

Plug the charger into the meter's female port and the device into the male port. Start the capture before connecting the device, then connect it during the window:

powerz measure -duration 20s -json
# .pd.source_capabilities[]  -> offered PDOs (fixed/PPS/AVS, V, A, W)
# .pd.contract               -> the request acknowledged with PS_RDY
# .vbus_v.last               -> the voltage actually on the bus

Is a meter connected, and which one?

powerz devices -json      # {"count":1,"devices":[{"serial":"050002",…}]}

Handling failures

  • Exit 4 or 5: retry. Pass -wait 10s to avoid exit 4 altogether.
  • Exit 3: ask the human to connect the meter.
  • Exit 7: the JSON on stdout is still valid; check errors / last_error.
  • Do not run two powerz commands against the same meter in parallel.

8. Safety model

Every frame is checked against a whitelist (km003c/guard.go) right before it goes to the device. Only these frames are allowed:

  • GET_DATA for ADC, settings and the PD buffer, on the vendor bulk interface. Only the ADC read is allowed on HID and CDC.
  • CONNECT.
  • MemoryRead of exactly three fixed 64-byte information blocks.

Never sent: settings writes, factory reset, firmware/DFU commands, authentication, stream start/stop, and the CDC text commands that make a charger raise VBUS. powerz cannot change the voltage on the bus.

Learned the hard way: the meter stalls, and its watchdog reboots it, if a new request arrives while a previous reply or zero-length packet is still queued on its IN endpoint. powerz consumes the zero-length packet after MemoryRead data and drains the endpoint after any failed or timed-out exchange before writing again. Regression tests in km003c/device_test.go cover both cases.

9. Caveats

  • IBUS sign convention: which direction is positive has not yet been verified with a known load. Energy and charge are signed accordingly.
  • Detected fast-charge protocol: the meter's D+/D− dashboard labels are reproduced exactly (inferred.dashboard_label*). Protocols the meter detects by sniffing (AFC, FCP, SCP, UFCS, VOOC) are kept only in firmware RAM and are not exposed over USB. USB-PD details come from pd and the pd section of measure.
  • IBUS sign: the official app and open-powerz state that negative means current flowing from the meter's female receptacle to its male plug. This has not yet been checked on a bench with a known load.
  • Polling rate: the meter samples at its configured rate (2, 10, 50 or 1000 SPS, see info). Polling faster only repeats values.
  • PD buffer: reading PD drains the meter's PD buffer, so only one consumer sees each record.
