Hazard observed on this unit (fw 1.9.5): never write while EP 0x81 still holds data

If the host sends the next request while a reply is still queued on bulk IN EP 0x81, the meter never answers. Its USB stack stalls and the watchdog reboots it; the device then re-enumerates. The queued item can be the zero-length packet (ZLP) that ends a MemoryRead, or any unread reply. Our client hit this once.

  • After a MemoryRead: read the 20-byte C4 confirmation, then the data transfer, then the trailing ZLP, before writing again (§9.2).
  • After any timed-out or failed exchange: drain EP 0x81 with short reads until a read times out, then write the next request.
  • Keep one request in flight at a time.

Evidence: a ZLP follows each MemoryRead data transfer in active_bulk_log.json (W6#1–W6#3, see testdata/fw1.9.5/INDEX.txt). The stall and reboot were observed by the team during a client run; no capture file exists for it.

1. TL;DR for the Go client

  1. Primary transport: IF0 vendor bulk, OUT endpoint 0x01, IN endpoint 0x81.

    • The Linux kernel driver uses this interface source K powerz.c:17-18, 126-130, 264-268.
    • On macOS, libusb can claim IF0 without detaching a driver notes O protocol.md:58-61.

  2. Read the ADC once. Write the 4 bytes 0C <id> 02 00 and read one bulk transfer. The reply is 52 bytes (48 on older firmware): 41 <id> xx xx + 01 00 00 0B + a 44-byte payload.

    • The kernel driver sends exactly 0c 00 02 00 with no CONNECT, no authentication and no reset source K powerz.c:121-130.
    • The vendor PDF shows the same request bytes vendor-doc V1 p.3. The vendor's own C++ sample sends them over HID with nothing before them source VS hiddemo.cpp:230-252.

  3. No handshake is needed for ADC or PD polling.

    • ADC on bulk: the kernel driver sends no CONNECT source K powerz.c:110-150.
    • PD on bulk: I polls PD_PACKET over IF0 without CONNECT source I transport.py:228-283, km003c_cli.py:817, and its README reports a working USB PD capture on hardware notes I README.md:354.
    • SETTINGS: shown to work without CONNECT only on CDC notes O protocol.md:378-382, 777-778. Whether SETTINGS on bulk works without CONNECT is unverified; send CONNECT first if it fails.

    Authentication (0x4C, AES) only matters for:

    • streaming control, which is AdcQueue start/stop and the PD sniffer;
    • TICK and the offline-record list;
    • writes.

    CONNECT (0x02) is only needed on bulk, before a MemoryRead, which is how the device-info blocks are read (§9).

  4. HID (IF3, interrupt endpoints 0x05/0x85) is ADC-only. Send exactly one request, 0C <id> 02 00, zero-padded to 64 bytes.

    • A reply longer than 64 bytes hangs the firmware, and the watchdog reboots the meter 1.5–3.5 s later notes O protocol.md:741-769, firmware 2.0.6.
    • The O library's HID transport refuses every other request source O transport/hid.rs:49-63.

  5. Avoid CDC (IF2) for the binary protocol. On CDC:

    • bytes 0x01, 0x02 and 0x03 start, keep alive and stop the vendor "ADCNEW" stream;
    • the same byte stream carries the ASCII "PDM" trigger commands, which change VBUS.

    The CDC trigger-command list is in vendor-doc V2 p.1-2 and notes O protocol.md:771-970. The rule that CDC refuses frame types 0x01–0x03 is in source O transport/cdc_frame.rs:30-36.

  6. Never send these frame types: 0x04, 0x08, 0x09, 0x0A, 0x42, 0x48, 0x4A, 0x4B, 0x4D (§12). They are taken from:

    • the O command guard source O transport/guard.rs:18-27;
    • the R/RR firmware notes notes RR docs/firmware/handlers.md:18-37.

Interfaces and endpoints

The endpoint addresses agree across sources: source R device.rs:143-151, source I transport.py:115,123, notes O protocol.md:45-50, notes RR usb_transport.md:116-126.

IF Class Endpoints Carries
0 0xFF vendor bulk OUT 0x01, bulk IN 0x81 (64 B packets) The full binary protocol. Every documented feature works here.
1 0x02/0x02 CDC ACM interrupt IN 0x83 (8 B, 10 ms) CDC notifications only
2 0x0A CDC data bulk OUT 0x02, bulk IN 0x82 One shared byte stream with three uses: the binary protocol (GET_DATA works), the ADCNEW push stream and the ASCII PDM trigger commands. macOS exposes it as /dev/cu.usbmodem*.
3 0x03 HID, usage page 0xFF00 interrupt OUT 0x05, IN 0x85 (64 B, 1 ms) One 64-byte input report and one 64-byte output report, no report ID. Only the ADC snapshot is safe here.

Source C's endpoint map does not match the KM003C layout. source C record.py:59-64 pairs IF1 with 0x05/0x85 and IF3 with 0x03/0x83. That disagrees with R, I, O and RR. Interface numbering reportedly differs between models (the KM002C is said to put HID at IF1) notes O protocol.md:52-54.

Select interfaces by class (0xFF vendor, 0x03 HID, 0x0A CDC data), not by number, and read the endpoint addresses from the configuration descriptor.

Vendor statement about transports

vendor-doc V1 p.1 says there are three interfaces, and that the same commands work on all of them:

Interface Stated throughput
WinUSB / "USB USER" 200 KB/s
CDC (baud rate is ignored) 200 KB/s
HID (data limited to 64 bytes) 60 KB/s

On the extended-header size field, the two vendor sources disagree:

  • The PDF says it must not exceed 1024−8 bytes, chunk*size must not exceed 4080, and the HID interface must not exceed 60 vendor-doc V1 p.1.
  • The vendor sample code says "must not exceed 4095−8 bytes; CDC and HID less than 64 bytes" (不能超过4095-8个字节 CDC HID 小于 64字节) source VS hiddemo.cpp:91.

Device observations on firmware 2.0.6 show that "same commands everywhere" is only partly true notes O protocol.md:55-57, 741-783. On CDC, a 188-byte SETTINGS reply was observed to work, contrary to the VS comment (§14 C21).

Vendor endpoint selection. The VS demo enables libusb_set_auto_detach_kernel_driver, claims every interface, and picks endpoints by transfer type: the first interrupt IN/OUT is "hid", and the first bulk IN/OUT is "user" (IF0, which comes before the CDC bulk pair) source VS hiddemo.cpp:133-224.

Transport framing rules

Bulk (IF0)

  • One request is one OUT transfer.
  • One response is one IN transfer, delimited by a short packet.
  • R reads into a 2048-byte buffer and joins transfers until a short packet source R device.rs:155, 718-741. I reads with a 65536-byte buffer source I transport.py:121-127.
  • The vendor app sends a zero-length packet after any OUT write whose length is a non-zero multiple of 64 notes O protocol.md:62-64; source O transport/bulk.rs:19-23. Requests in the safe set are 4 or 36 bytes, so this never applies to them.

Stale data at open (bulk)

A stale DISCONNECT (03 xx 00 00) often waits on EP 0x81 when the device is opened. Drain the IN endpoint with short reads until one times out source O transport/bulk.rs:25-36, notes O protocol.md:142, 709.

HID (IF3)

  • Output report: 64 bytes, request zero-padded. Through hidapi you write 65 bytes, where byte 0 is report ID 0x00. That leading 0x00 is a hidapi convention and is not sent on the wire source O transport/hid.rs:66-73, source I transport.py:43-50, source NV constants.py:29.
  • Input report: 64 bytes, response zero-padded, no report-ID byte notes O protocol.md:743-745.
  • Linux hidraw: N writes the bare 4-byte request to /dev/hidraw* and reads 64 bytes source N connection.py:143-152, meter.py:191-193.

CDC (IF2)

  • Bytes are written to the tty. The baud rate is ignored vendor-doc V1 p.1. The vendor tools use 2 000 000 8N1 notes O protocol.md:774-775.
  • Replies, ADCNEW frames and PDM text lines can be interleaved on the same stream. Demultiplex by header and id notes O protocol.md:820-828, source I transport.py:243-266.

Every frame begins with one 4-byte little-endian u32. Bit 0 is the least significant bit of byte 0. The same word is read in one of three views.

Encoding. word = type | id<<8 | att<<17, then write it little-endian.

The same formula appears in three sources: source N protocol.py:90, source I protocol.py:62-65, source O frame.rs:240-245.

Because att starts at bit 17, the att value shows up doubled in byte 2:

  • att 1 encodes as 02 00;
  • att 0x10 encodes as 20 00;
  • att 0x200 encodes as 00 04.

The ADC request built this way is 0C 00 02 00 in four places: source K powerz.c:121-124, vendor-doc V1 p.3, source R tests/adc_tests.rs:74-90, source C record.py:11.

3.3 Extended (section) header

Each logical section inside a PUT_DATA starts with its own 4-byte header.

 bit: 31          22 21     16 15 14                          0
      +-------------+---------+--+----------------------------+
      | size (10)   |chunk (6)|nx|       att (15 bits)         |
      +-------------+---------+--+----------------------------+
Bits Field Meaning
0–14 att The single attribute bit this section answers
15 next 1 means another section follows
16–21 chunk Record count for ADC_QUEUE, so at most 63 records per reply
22–31 size Payload bytes. For ADC_QUEUE this is the record size (20).

The layout is the same in vendor-doc V1 p.1, source R packet.rs:47-54, source O frame.rs:278-306, source I protocol.py:100-122 and source N protocol.py:113-129.

Section payload length:

  • ADC_QUEUE: chunk * size source O frame.rs:296-304, source R packet.rs:491-501.
  • PD_STATUS (0x020) and RECORD_LIST (0x200): the size field is 0 or unusable, so the payload is the rest of the frame source O frame.rs:379-393. R derives the 0x020 boundary from queue prefixes instead source R packet.rs:492-493.
  • Every other attribute: size.

Section order. Sections arrive in ascending attribute-bit order. An attribute that is gated, or has nothing to report, is left out notes O protocol.md:128-130. An empty PUT_DATA is a bare 4-byte header such as 41 id 00 00. Bits 17–18 may be non-zero in it, as in 41 id 02 00 source R packet.rs:448-456, notes O protocol.md:196-198, 737.

Worked decode of a section header.

  1. 01 00 00 0B is the LE word 0x0B000001.
  2. att = 0x0B000001 & 0x7FFF = 1 (ADC).
  3. next = (word >> 15) & 1 = 0.
  4. size = 0x0B000001 >> 22 = 44.

source R tests/adc_tests.rs:12-26; source O tests/vectors/adc_52.hex.

6.5 Recipe: "read ADC once" (bulk IF0)

  1. Find 5FC9:0063, open it and claim interface 0.
    • Linux: detach powerz first.
    • macOS: no detach is needed notes O protocol.md:58-61.
    • Do not USB-reset the device. R resets by default and then waits 1.5 s source R device.rs:510-521; nothing requires a reset. K never resets.
  2. Drain EP 0x81: read with roughly a 50–100 ms timeout until a read times out, discarding anything that arrives (for example 03 xx 00 00) source O transport/bulk.rs:25-36. Do the same after any timed-out or failed exchange, before the next write. On the user's unit, writing while EP 0x81 still held a reply or ZLP stalled the meter and caused a watchdog reboot; see the hazard box at the top device fw 1.9.5.
  3. id := next u8. Any value works; K uses 0. Write 0C id 02 00 (4 bytes) to EP 0x01.
  4. Read EP 0x81 into a buffer of at least 2048 bytes, with a 1 s timeout.
    • K waits only 5 ms source K powerz.c:134-135.
    • RR measured a median ADC latency of 164 µs notes RR protocol_reference.md:694.
    • The vendor app uses 1000 ms (2000 ms for CONNECT) notes O protocol.md:738.
  5. Validate the reply:
    • len >= 8.
    • b[0] & 0x7F == 0x41. If it is 0x03 (DISCONNECT) or 0x06 (REJECT), retry once.
    • b[1] == id. If the id differs, the frame is stale: skip it and keep reading until the timeout. Then drain EP 0x81 before the next write (§14 C6, resolved on fw 1.9.5).
    • ext := LE32(b[4:8]), ext & 0x7FFF == 1, and size := ext >> 22 is at least 36.
    • len >= 8 + size.
    • A 4-byte 41 id .. reply means empty: retry.
  6. Decode b[8 : 8+size] with the table in 6.2.
  7. Pacing:
    • Keep one request in flight.
    • The vendor app polls ADC about every 200 ms notes RR protocol_reference.md:614-621.
    • O uses at least 60 ms between requests notes O protocol.md:718-719.

HID variant (IF3).

  • Write the 64-byte output report 0C id 02 00 followed by 60 × 00. Through hidapi that is a 65-byte buffer starting with 00.
  • Read one 64-byte input report and parse it as above. Bytes after 8+size are zero padding.
  • Do not send anything else over HID source O transport/hid.rs:49-73, source N meter.py:178-204.
  • The vendor's own sample does exactly this source VS hiddemo.cpp:230-252, 266-291. It sends a 64-byte interrupt OUT transfer whose first 4 bytes are 0C 00 02 00 (id always 0), reads one 64-byte interrupt IN transfer, uses a 1000 ms timeout and polls every 150 ms. It checks type == 0x41 and section att == 1, and displays Vbus_avg and Ibus_avg.
    • In that sample, bytes 4–63 of the OUT buffer are uninitialised stack memory, so the firmware evidently ignores them. Zero-pad anyway.
  • O also reports that control commands (CONNECT, 0x0E, 0x0F, 0x44, 0x4C) get no reply over HID notes O protocol.md:754-756.

CDC variant (not recommended).

  • Write 0C id 02 00 to the tty and read until a full 52-byte frame matches the id. I's hardware check confirmed it works notes I README.md:354; source I transport.py:268-283.
  • Never write 0x01, 0x02 or 0x03 frames there.

9.2 MemoryRead (0x44): bulk only, after CONNECT, known addresses only

Preconditions:

  • Bulk IF0 only. Over HID there is no reply; over CDC there is no reply, and CONNECT there starts ADCNEW notes O protocol.md:477-484, 754-756.
  • CONNECT is required first. Without it the device answers 06 id 00 00 REJECT. This was observed on firmware 2.0.6 notes O protocol.md:478-482, and O enforces it in code source O session/memory.rs:219.
  • No authentication is needed notes O protocol.md:477-478. The firmware 1.9.9 decompilation shows no auth check on 0x44 notes RR handlers.md:172-200.

Request (36 bytes): 44 id 01 01 followed by AES-128-ECB(key0, P).

  • Bytes 2–3 01 01 are a raw header word. Do not build them with the att<<17 encoder source R message.rs:516-523, notes RR protocol_reference.md:154-155.
  • P is 32 bytes of plaintext:
Off Field
0x00 u32 address
0x04 u32 length
0x08 u32 0xFFFFFFFF
0x0C u32 CRC-32 (IEEE, as zlib crc32) of P[0:12]
0x10 16 × 0xFF

Sources: source R auth.rs:271-292; source O crypto/mod.rs:15-51; notes O protocol.md:486-495.

  • key0 = ASCII Lh2yfB7n6X7d9a5Z = 4C 68 32 79 66 42 37 6E 36 58 37 64 39 61 35 5A. It appears in source RR km003c_analysis/device/protocol.py:76-77 and as KEYS[0] in source O crypto/keys.rs:10-13.

Reply:

  1. A 20-byte framed confirmation: C4 id <b2> 01 followed by the plaintext echo of P[0:16] (address, length, magic, CRC).
    • Type 0x44 has the extend bit set, which gives C4.
    • b2 bit 0 is the encrypted flag.
    • Sources: source R auth.rs:312-358, memory.rs:115-168; notes O protocol.md:497-502.
  2. Then unframed transfer(s) totalling roundup16(length) bytes. If the flag is set, decrypt them with AES-128-ECB key0 and truncate to length source R memory.rs:29-113.
  3. Then a zero-length packet, observed after a 64-byte (multiple-of-64) data transfer. Read it before writing the next request; leaving it queued stalls the meter and triggers a watchdog reboot (see the hazard box at the top).
    • On this unit: the confirmation arrived after 1.1–1.4 ms, the 64-byte ciphertext 14.5–15.2 ms after the request, then the ZLP.
    • device fw 1.9.5 bulk_W6_1_resp.hex, bulk_W6_1_respdata.hex, INDEX.txt

Errors:

  • 06 REJECT: missing CONNECT, or bad magic, size or address.
  • 27 NOT_READABLE: bus fault.

Sources: source R memory.rs:43-55, device.rs:179-187; notes RR handlers.md:183-209.

Chunking and pacing:

  • Use at most 256 bytes per request. O observed truncation above that on 2.0.6 notes O protocol.md:504-509; R uses a 2528-byte chunk source R memory.rs:14 (§14 C11). The info blocks are only 64 bytes.
  • Space reads at least 50–100 ms apart notes O protocol.md:520-521.
  • Do not read while AdcQueue streaming is active source R device.rs:1155-1162.

Known addresses: the whitelist. Do not read any other address. Third parties report that other peripheral addresses crash the meter notes O protocol.md:520-521, 1241.

The firmware itself does not restrict addresses; the client-side whitelist is the only protection.

  • The MemoryRead handler checks only three things: magic = 0xFFFFFFFF, size < 0x3D0901, and address < 0x983D0901.
  • There is no lower bound and no allow-list, so peripheral registers can be read. Reading some registers has side effects, such as FIFOs and clear-on-read status registers.
  • Sources: firmware analysis §11 (1.9.5 through 2.0.7, identical logic), and notes RR handlers.md:172-200 (1.9.9).

Check the confirmation against the request. The confirmation echoes the address and length. The client must reject a C4 confirmation whose address or length differs from what was requested, and must not read the following data as the requested block.

  • One case where they differ: the firmware may redirect reads inside the OTP window 0x03000C00–0x03000D7F to 0x03000D80 (firmware analysis §11).
  • R performs the same check source R memory.rs:143-148.
  • After a rejected confirmation, drain EP 0x81 before writing again: the ciphertext and the zero-length packet will still arrive (see the hazard box at the top).

10. Authentication (0x4C): what it gates

Request (36 bytes): 4C id 00 02 followed by AES-128-ECB(key3, P32).

  • Bytes 2–3 00 02 are a raw word: 0x0200 source R message.rs:524-531, source O session/auth.rs:48-53.
  • key3 = Fa0b4tA25f4R038a source RR protocol.py:78-79, source O crypto/keys.rs:22-25 (KEYS[3]).
  • The P32 plaintext differs by source; per the 1.9.9 decompilation, only the credential bytes are checked:
Source P32 layout
source R auth.rs:383-403 [u64 LE ms timestamp][12-byte credential][12 random bytes]
source O session/auth.rs:17-28 [u64 ms][credential (≤16 B)][u64 random], padded with 0xFF

Credential check: notes RR handlers.md:76-96.

Reply: 4C 00 <lo> <hi> followed by 32 bytes.

  • The id is always 0 source R auth.rs:37, device.rs:1036-1050.
  • The raw word bytes 2–3 hold: bit 0 = result/encrypted flag; bits 1–2 = auth level.
    • 0x0201 = level 0 (failed).
    • 0x0203 = level 1.
    • 0x0205 = level 2.
    • source R auth.rs:31-35, 468-495; notes RR handlers.md:98-102.
  • The payload is the plaintext re-encrypted with FX0b4tA25f4R038a (key3 with byte 1 = X) source O session/auth.rs:55-83, notes RR features/authentication.md:93-98.

Credentials:

  • Level 1: the 12-byte UID read from 0x40010450.
  • Level 2: a calibration credential. Sources disagree on which bytes (§14 C13).
  • Behaviour: HID gets no reply. The level is lost when the device is reopened. Keep requests at least 1 s apart. notes O protocol.md:686-697; source O session/auth.rs:11-12

11. CDC-only behaviour: ADCNEW and PDM text (do not use)

ADCNEW stream

  • Frames: [type=0x02][att][obj = body words][crc8], then 20-byte records (u32 ms, i32 µV, i32 µA, 4 × u16).
  • Start: 02 alone, or 02 <att> where the high nibble is the content and the low nibble is the rate.
  • Keep-alive: 01. Stop: 03.
  • The stream stops after one hour unless refreshed.

Sources: source I transport.py:286-338, protocol.py:310-327; notes O protocol.md:784-828.

Conflict: I says the CRC-8 algorithm is undocumented and leaves it unverified on hardware notes I README.md:198-206. O reports poly 0x29, init 0 notes O protocol.md:800.

Classification: MODE, CDC only. Not needed.

PDM text commands

These are lowercase ASCII, one command per write, with no terminator. Examples:

  • pdm open and pdm close;
  • pdm set type=..,em=..;
  • entry pd|qc|ufcs|fcp|scp|afc|vfcp|sfcp;
  • qc 9V, qc3 volt=..., pd req=..., pd cmd=..., pd data=...;
  • reset.

Sources: vendor-doc V2 p.1-2; source I transport.py:341-371; notes O protocol.md:830-970.

All of them are UNSAFE-POWER:

  • pdm open makes the meter present Rd as a sink.
  • The entry and request commands negotiate higher VBUS with the charger.
  • entry list actively probes the charger and can raise VBUS notes O protocol.md:844-873.

13. "Detected fast-charge protocol" (shown on the screen)

No source exposes it as a binary read.

  • None of the GET_DATA attributes documented by V1, R, RR or O carries the protocol name the meter shows on screen.
  • The vendor name ATT_QC_PACKET (0x040) is a UFCS sniffer stream, not a detection result (§7.4). The name is not evidence.
  • The only documented detection path is the CDC text command entry list, and the per-protocol entry bc / entry apple. These actively probe the charger and can raise VBUS notes O protocol.md:865-873, 901-912. They are UNSAFE.

What a client can do instead, as inference only and labelled as such:

  • show D+/D− voltages from the ADC (§6.2), for example BC1.2 or Apple divider levels;
  • show passively captured PD Source_Capabilities, which appear in the PD records (§7.2) when the meter takes part in a negotiation.

C1 – ADC tail 0x24–0x2B. There are three layouts:

  • V1: Rate:2 at 0x24.
  • R and L (firmware 1.9.x): rate at 0x24, flags at 0x25, then CC2/D+/D− averages.
  • O (firmware 2.0.6): T2 i16 at 0x24, rate at 0x26, battery at 0x28.

The captured vectors fit different layouts (§6.3), so the layout is firmware-dependent.

To resolve without changing anything: read SETTINGS and compare bits 2–3 of the u32 at 0x60 with ADC bytes 0x24 and 0x26. Also read the 0x4420 block to learn the firmware version.

C2 – Sample-rate field offset. It is 0x24 (V1, R, I) or 0x26 (O). Same evidence as C1.

C3 – IBUS sign convention.

  • R: positive = power flows from the USB female (input) side to the male (output) side source R adc.rs:98-104.
  • O: negative = current from the receptacle (female) to the plug (male) notes O protocol.md:219.

These are opposite. K only says the sign shows direction source K Documentation/hwmon/powerz.rst. To resolve: one measurement with a known load direction.

C4 – Temperature.

  • R and O: i16/128 °C. O adds 0x8000 = invalid.
  • K: b1*2000 + b0*1000/128 m°C, which is wrong for negative raw values.
  • V1 example: raw 0.
  • NV: raw/100 source NV constants.py:51. It also masks CC/D± with 0x0FFF and divides by 1000 source NV constants.py:54-57, which contradicts every other source. Disregard NV's scalings.

C5 – Data-header bytes 2–3 (obj, permi).

  • permi is settled. The vendor sample code declares encode:1, permi:2, :3, obj:10 source VS hiddemo.cpp:76-85. This matches O's reading that bits 17–18 hold the auth level. The PDF still shows the older unnamed :6 vendor-doc V1 p.1. In the V1 example 41 09 02 02 and in R's EXTENDED_ADC_DATA, permi = 1, which suggests those captures came from authenticated sessions.
  • obj is still in conflict:
    • V1 and VS: payload size in 4-byte words.
    • R: len/4 − 3.
    • O: about (len−12)/4, with exceptions.
    • The V1 example has obj = 8 for a 48-byte frame, where the R formula gives 9.

Treat obj as opaque. Treat permi as diagnostic only.

C6 – Transaction-id echo.

  • R and O (device) observe the request id echoed; R matches on it source R device.rs:167-169.
  • Exceptions: the 0x4C auth reply and the HEAD reply carry id 0.
  • The vendor app never checks ids notes O protocol.md:721-722.
  • The V1 example shows request id 0 and reply id 9. It is probably not the same exchange.
  • The vendor sample always sends id 0 and checks only the type and section att source VS hiddemo.cpp:235-237, 275. Its own comment nonetheless says the id "keeps incrementing" source VS hiddemo.cpp:72.
  • I matches on type only source I transport.py:274-279.

Resolved (fw 1.9.5). The user's unit echoed the request id on 20 of 20 replies, including the CONNECT ACCEPT and the MemoryRead C4 confirmation (§6 and §14 "Verified on device").

Recommendation: match replies on type AND id.

  • Why not type only: a stale reply that arrives after a retry would be taken as the retry's answer. The retry's real reply then stays queued on EP 0x81, and the next write stalls the meter (see the hazard box at the top).
  • What the powerz client does: it skips frames carrying a foreign id, keeps the last frame of the wanted type only as a fallback, and drains EP 0x81 before the next write.
  • Exceptions that keep id 0: the 0x4C auth reply and the HEAD reply. The client never sends those requests.

C7 – Level-0 gating. On 1.9.9 the decompilation masks the attributes to 0x19 notes RR handlers.md:110-113. On 2.0.6, AdcQueue, 0x020 and 0x040 are served at L0 notes O protocol.md:203-206.

C8 – PD over HID.

  • R presents HID as an "ADC/PD polling" mode source R device.rs:196-224.
  • NV sends PD over HID by default.
  • I got no reply to PD-only requests over HID.
  • O observed hangs and reboots for any reply over 64 bytes.

Decision: HID is ADC-only.

C9 – Names of 0x020 and 0x040. V1 calls them ATT_PD_STATUS and ATT_QC_PACKET. R calls 0x020 PdTrace. RR and O treat 0x040 as UFCS.

C10 – AdcQueue record bytes 0–3. R reads u16 sequence + u16 marker source R adcqueue.rs:125-127. O reads a u32 ms time and says R's reading is wrong source O decode/queue.rs:27; notes O protocol.md:285.

C11 – MemoryRead chunk limit. R uses 2528 bytes source R memory.rs:14. O observed 256 notes O protocol.md:504-509. Use ≤ 256.

C12 – Meaning of the 0x420 block. R says model, hardware version and manufacturing date (24 B) source R auth.rs:165-178. O says model, version ("2.5", likely bootloader), date (12 B) and extra source O decode/info.rs:26-40.

C13 – Level-2 credential. R uses the first 12 bytes of the calibration record at 0x03000D80, falling back to 0x03000C00 source R device.rs:1095-1138. O uses the first 16 bytes of the OTP at 0x03000C00 source O session/auth.rs:14-38. This does not matter for a read-only client.

C14 – StreamingAuth plaintext layout. The two sources lay out the bytes after the credential differently (§10). Only the credential is checked.

C15 – PD connection events.

  • R: marker 0x45, a 24-bit timestamp at +1..+3, and code 0x21 / 0x22 = connect / disconnect, with 0x11 / 0x12 as "legacy" source R pd.rs:202-219.
  • O and L: generic event records with a u32 timestamp. The code byte's low nibble is the event and the high nibble the CC line, so 0x11 / 0x21 = attach on CC1 / CC2 source O decode/pd_packet.rs:255-322; source L km003c.pas:283-295.

C16 – CONNECT necessity. K, N, I and O show that the ADC needs no CONNECT. R's vendor mode always sends CONNECT plus a full init, including a USB reset. Decision: send CONNECT only before MemoryRead.

C17 – Unreliable sources. C's endpoint map and NV's scalings contradict the descriptors and every other source. They are kept only for completeness.

C18 – Bulk replies that are an exact multiple of 64 bytes. It is unknown whether the device ends them with a zero-length packet. A large read buffer plus a timeout is the robust approach. R's until_short_packet would error without a ZLP source R device.rs:722-729.

C19 – Vendor control request 0xC2/0x32, wLength 170. Seen during enumeration in VM passthrough; semantics unknown notes RR usb_transport.md:222-227. Do not send it.

C20 – Firmware of the local unit. Unknown. Learn it with W5 and W6 at 0x4420, which also helps decide C1, C2, C7 and C11.

C21 – Section-size limits in the vendor material.

  • PDF: size ≤ 1024−8, chunk*size ≤ 4080, HID ≤ 60 vendor-doc V1 p.1.
  • Sample code: size ≤ 4095−8, and "CDC and HID less than 64 bytes" source VS hiddemo.cpp:91.
  • O observed 188-byte SETTINGS replies working over CDC notes O protocol.md:777-778.

The HID limit is consistent across all of them. On CDC, prefer replies under 64 bytes (ADC only) unless the device agent confirms longer replies are safe there.
