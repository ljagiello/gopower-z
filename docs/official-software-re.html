POWER-Z KM003C: what ChargerLab's official software sends

How the official Windows software talks to the KM003C (USB VID 0x5FC9, PID 0x0063), as input for an interoperable Go client. Primary target: the user's POWER-Z Lab 3.0.0 (powerz_km_win_3.0.0/qt6_x64/POWER-Z.exe). Cross-reference: POWER-Z Lab 2.5.2 (Mtools.exe, PDM.exe), the official SDK sample and PDFs. Nothing here was tested against a device.

Citation key. P3 FUN_…: POWER-Z 3.0.0 POWER-Z.exe. Mt FUN_…: 2.5.2 Mtools.exe. PDM FUN_…: 2.5.2 PDM.exe. All three are Ghidra 12.2 headless decompiles; the address is the function VA, and L<n> is a line number in that decompiler's C output. docx: the official KM002C&3C API Description.docx. capture: a USBPcap recording of the official 2.5.x app talking to a KM003C. These are third-party captures (repo okhsunrog/km003c-protocol-research, usb_master_dataset.parquet), used only to validate decompiled logic. CONFLICT marks a contradiction between sources; it is left unresolved.

1. Key findings

  1. POWER-Z 3.0.0 (the user's build) splits by interface:
    • Live dashboard and recording use the CDC serial port with a newer framing, type 0x15:
      • Header bits: seq nibble at 8–11, length at 12–23, sub-command at 24–31. Replies set bit 7, so they start 0x95.
      • Sub-commands: 01 info, 02 auth, 05 set (att 0x32 = stream start/stop), 07 ADC records (polled every 10 ms), 08 Type-C/PD/UFCS state logs (unused).
    • libusb/IF0 is used only for firmware update and factory provisioning, which includes a new 0x43 OTP-ID write.
    2.5.2 used IF0 bulk for everything. Details in §3.
  2. Transport (2.5.2). libusb bulk on IF0 (vendor class, WinUSB): EP 0x01 OUT, 0x81 IN. CDC (IF1/2) carries the same binary commands plus a text "PDM" protocol-trigger language. HID (IF3) carries the same binary commands in 64-byte reports.
  3. Bring-up, confirmed by the 2.5.2 decompile and capture:
    1. CONNECT.
    2. Four AES-encrypted memory reads: 0x420, 0x4420, 0x3000C00, 0x40010450.
    3. An AES challenge-response 0x4C keyed on the MCU UID.
    4. GET_DATA(Settings), then GET_DATA(RecordList), then STOP_QUEUE.
    5. Poll GET_DATA with an attribute bitmask.
  4. Auth is enforced by the device for streaming. In the capture the meter answers START_QUEUE (0x0E) with REJECT (0x06). The app then re-runs CONNECT, the UID read and 0x4C, and the retry succeeds. The decompile has the same recovery path (Mt FUN_14007c640 L65782–65788). Which other commands are gated cannot be determined from PC code.
  5. Keys. Hardcoded AES-128-ECB keys with 0xFF padding, all validated by decrypting captured traffic:
    • Lh2yfB7n6X7d9a5Z: memory reads, encrypted replies, firmware image.
    • Fa0b4tA25f4R038a: auth request. The reply uses FX0b4tA25f4R038a (byte 1 replaced by 'X').
    The same key strings are present in 3.0.0.
  6. ADC block. 44 bytes on current firmware, not the docx's 40. 3.0.0 exposes the tail as roles vsbu1/vsbu2, shown as TMP1/TMP2. Its UI says channel 1 = meter-internal temperature and channel 2 = external sensor (reserved); see §8.1.
  7. IBUS sign. Negative means current flows receptacle → plug. Source: the new-ADC PDF, and the 3.0.0 UI text "KM003C电流从[母座]流向[公头]就是反电流". 3.0.0 has an optional "absolute current |A|" mode and a separate polarity indicator.
  8. Detected fast-charge protocol. Neither PC version has a code→name table for the on-screen "detected protocol". The PC triggers detection only through CDC text commands (entry …), all of which change device state.
  9. Unsafe commands exist (§14):
    • JUMP_APROM/DFU (0x08/0x09), firmware download (0x40/0x42 plus 4080-byte chunks), flash write 0x4A, SET_DATA 0x48.
    • PDM settings write 0x0A (key 8 = factory reset).
    • 3.0.0 setOtpID/allocOtpID (writes the device ID).
    • Every CDC text command, including undocumented pd hrst.
    • 2.5.2 auto-sends JUMP_DFU when the HEAD reply word is non-zero.

3. POWER-Z 3.0.0 specifics

Filled in from the 3.0.0 decompile; see the sub-sections below.

3.0.0 is a different program from 2.5.2. It is a QML "MultipleRecord" multi-meter recorder with a firmware-update and factory-provisioning window. It has no PD analyzer and no protocol trigger. Ghidra decompiled 3691 functions; the class names come from RTTI and Qt moc metadata.

3.3 3.0.0 connect and dashboard sequence (CDC)

  1. Open the COM port (FUN_140110ab0).
  2. 0x15/01 info query (FUN_140110d50). This fills the info list and decides "private" (+0x20e), see §3.5.
  3. 0x15/02 auth (FUN_140112aa0), which sets +0x20d.
  4. Start a 10 ms timer named "adc" (L197809). On each tick, if +0x20d is set:
    • "private": send 0x15/07.
    • Otherwise: send Modbus RTU fn 4 "read input registers 0, count 10" (00 00 00 0a, FUN_140106690), which is for non-KM products.
  5. Recording start/stop sends 0x15/05 att 0x32.
  6. The dashboard shows VBUS, IBUS (with a polarity badge), PWR, DP, DM, CC1, CC2, TMP1, TMP2 (QML roles vbus ibus polarity power vdp vdm vcc1 vcc2 vsbu1 vsbu2, DevView.qml).

Developer log qt6_x64/log/2025-03-17.txt:

  • USB串口插入 "COM4" ("USB serial port inserted") and USB插入 "\\?\USB#VID_5FC9&PID_0063#001590#{A5DCBF10-…}" (serial 001590).
  • 1624 × missN N, the gap detector in FUN_1401122d0.
  • The firmware window logs "02010000" "03010000": CONNECT answered by DISCONNECT. That most likely happened while the CDC session held the meter.

The four u16 values are in record order, which matches the new-ADC PDF's Vcc1, Vcc2, Vdp, Vdm; the code itself just labels them x1–x4. Snippet:

dVar27 = (double)*(int *)(pcVar9 + lVar14 + -8) / 1000000.0;      // Vbus

  if (*(short *)(pcVar9 + lVar14 + 8) == -0x8000) dVar34 = -0.009;

At rates of 1 ms or faster each record is emitted directly. At slower rates the app averages rate/1000 records, so the meter streams at 1 kSPS and the PC decimates. The QML rate options are 0.1/1/10/100/1000 SPS, stored in µs. The "Temp" option is disabled at 1 kSPS. Its tooltip translates as "Channel 1: meter internal (disabled at 1 ms sampling); Channel 2: external sensor (reserved channel, needs latest meter)".

3.5 3.0.0 device info and the "private" (genuine-device) check (P3 FUN_140110d50)

  • Reply layout: 64 B Boot block, 64 B App block, then OTP ASCII.
    • Each info block: u32@0 == FFFFFFFF → "none"; strings @0x10/0x1C/0x28/0x34 = name / version / date / plan.
    • OTP sections split by spaces: 0 = SN, 1 = UUID (shown truncated to 16 chars + ****), 2 = Unix factory date (rendered yyyy-MM-dd hh:mm:ss). "LYS" inside OTP[0x34..] → "true".
  • Labels (FwUpWindow QML): Boot name/version/date/plan, App name/version/date/plan, 出厂日期 (factory date), SN, Authorize, UUID, GUID, ROM2. hwVersion = Boot version, fwVersion = App version.
  • Genuineness check: the trailing 32 B are decrypted with key3 whose byte [2] is stepped from '0' up to 'z' until dec[0] == challenge secs. If dec[4] and dec[1] also match two OTP words, the device is "private": Authorize = "private" and +0x20e = 1.
  • Effect: only "private" devices are polled with the KM 0x15/07 command; others fall back to Modbus (L198285–198306, L199193).

5. Framing

Every message starts with a 4-byte little-endian header (docx MsgHeader_TypeDef, identical in every builder of both app versions):

ctrl view  : bits 0-6 type | bit 7 extend | bits 8-15 id | bit 16 encrypted | bits 17-31 att (15)
data view  : bits 0-6 type | bit 7 extend | bits 8-15 id | bit 16 encode | 17-18 permi | 19-21 rsvd | bits 22-31 obj (# u32 words)
sub-header : bits 0-14 att | bit 15 next | bits 16-21 chunk | bits 22-31 size (bytes per chunk)   (inside 0x41 payloads)
  • id: one global byte counter, pre-incremented per packet (Mt FUN_140078d70 L63739). The device echoes it, e.g. 02 01 00 00 → 05 01 00 00.
  • Bit 16: marks an AES/key0 payload on 0x44/0x4A requests, on the 0xC4 read-reply header and on encrypted 0x41 replies. It is not set on the 0x4C auth request, whose body is AES with key3.
  • obj in plaintext replies does not equal the payload length. Capture: ADC reply 41 0a 82 02 has obj = 10 but carries 48 bytes. Parse by sub-header size. The app uses obj*4 only as the decrypt length for encrypted replies.

7. Connect and dashboard request sequence

2.5.2 Mtools, confirmed byte-for-byte by capture orig_adc_1000hz:

H→D 02 01 00 00                         CONNECT            → D→H 05 01 00 00 ACCEPT
H→D 44 02 01 01 + 32B AES(key0)         read 0x420 /0x40   → c4 02 01 01 + echo, then 64B AES(key0) data
H→D 44 03 01 01 + …                     read 0x4420/0x40   → info strings (model, FW version, date)
H→D 44 04 01 01 + …                     read 0x3000C00/0x40 → OTP ASCII (serial etc.)
H→D 44 05 01 01 + …                     read 0x40010450/0xC → 12-byte MCU UID (one 16-B block)
H→D 4c 06 00 02 + 32B AES(key3)         auth               → 4c 00 03 02 + 32B AES(key3')
H→D 0c 07 10 00                         GET_DATA att 0x008 → 41 07 02 0b | 08 00 00 2d | 180B settings
H→D 0c 08 00 04                         GET_DATA att 0x200 → record list

H→D 0c 0a 02 00  (repeat)               GET_DATA att 0x001 → 41 0a 82 02 | 01 00 00 0b | 44B ADC

The same order appears in the decompile:

  1. DeviceItem Mt FUN_140011b10 runs sign_openUsb → sign_connectDev → 50 ms sleep → sign_headDev → queryInfo.
  2. DeviceView Mt FUN_14001db20 L16874–16888 then runs sign_readOtpInfo → sign_security(1) → sign_getData(3) → sign_enQueue(0,rate) (= STOP).

Live polling (Mt FUN_14007d200 L66107, the timerEvent):

  • Timer period: 10 ms in queue mode, 2 ms in analyzer mode.
  • Flags accumulate into +0x25a:
    • 0x001 every 200 ms.
    • 0x002 every [1000,200,100,32,10,…][rate] ms.
    • 0x010 every 5 ms in analyzer mode 1.
    • 0x040 every 50 ms in analyzer mode ≥ 2.
  • The app then sends one GET_DATA(att = flags) (disasm 0x14007d333).

START_QUEUE carries a rate index with sample periods [1000,100,20,1] ms. On a non-ACCEPT reply the app sends CONNECT, then readOtpInfo, then security(1), and retries. Capture pd_adcqueue_new shows exactly this sequence after an 06 REJECT.

3.0.0 differs: its live dashboard runs on the CDC port with the 0x15 protocol. The sequence is info 0x15/01, then auth 0x15/02, then 0x15/07 every 10 ms (§3.3). 3.0.0 never sends GET_DATA, 0x4C or START_QUEUE.

9. Authentication and crypto

  • Cipher: AES-128 with the standard tables (S-box @Mt 0x1402836c0). Each 16-byte block is encrypted independently (Mt FUN_14007d930), i.e. ECB.
  • Padding (Mt FUN_14007e970): mode 3 = the last partial block is padded with 0xFF. All protocol uses select mode 3.
  • Key selection: Mt FUN_140080d20(idx) slices 16 bytes out of an obfuscation string. The same strings and function are in PDM FUN_1400182a0, and the strings are in 3.0.0.
  • Validation: everything below was checked by decrypting captured traffic with a small AES/CRC-32 script.

9.1 Handshake 0x4C (on_security(mode), Mt FUN_14007c100 L65510)

plain[32] = u64 now_ms | middle[16] | u64 rand
            mode 1: middle = 16 B read from 0x40010450 (UID 12 B + 00 00 00 00)   ← used by the app
            mode 2: middle = first 16 B of OTP 0x3000C00
send  : 4c id 00 02 | AES_ECB(key3, plain)
accept: reply type 0x4C; dec = AES_ECB^-1(key3 with [1]='X', reply[4:36]);
        dec[0:8] == now_ms  &&  dec[24:32] == rand   (capture: dec == plain)

9.2 Memory read 0x44 (Mt FUN_14007cfb0 + FUN_140078ef0)

request: 44 id 01 01 | AES_ECB(key0, u32 addr | u32 len | u32 FFFFFFFF | u32 crc32(first 12 B) | 16×FF)
         crc32 = standard reflected 0xEDB88320 (table @Mt 0x140195ae0), e.g. 0x420/0x40 → 0x241b8c1b
reply  : c4 id 01 01 | plaintext echo of {addr,len,FFFFFFFF,crc}   (20 B)
         then IN transfers of AES_ECB(key0) data until len bytes; 0x06 = REJECT

Addresses the apps read: 0x420, 0x4420, 0x3000C00, 0x40010450, and 0x98000000+off (SPI flash; offline logs at 0x98100000+, Mt FUN_14007c050 disasm 0x14007c067).

9.3 PDM CDC memory-read variant (PDM FUN_1400d9490 L161624)

plain[48] = u32 addr | u32 len | u32 crc32(addr‖len) | 9 × u32 random
send      = 8c id 01 02 | AES_ECB(key0, plain)[0:44]          (GET_DATA, extend, encrypted, att 0x100)

9.4 3.0.0 serial auth

The serial path has its own authentication (§3.2, §3.5):

  • 0x15/02 sends AES_ECB(key0, rand×4 | 12 B from info | rand). The reply must echo rand1 at u32@4; this is the host authenticating to the device.
  • The 0x15/01 reply carries a block encrypted with a per-device key3 variant (byte [2] ∈ '0'..'y') that must echo the challenge and OTP words; this is the device proving it is genuine ("private").
  • Same key strings as 2.5.2: P3 FUN_14001ac20(idx). AES helpers P3 FUN_140019fd0 (setkey), FUN_140019fc0 (pad mode 3), FUN_140019e90 (encrypt), FUN_140019de0 (decrypt).
  • Not validated against a capture; no 3.0.0 serial capture exists.

10. CDC serial

10.1 Simplified streaming command (official doc/获取ADC数据新命令.pdf), SAFE READ

request (1–4 bytes; just "02" is valid):
  byte0 type:7|zero:1   01 keep-alive · 02 start ADC auto-upload · 03 stop
  byte1 att  hi nibble  0 ADC · 1 ADC+PD · 2 ADC+UFCS · 3 ADC+PD/UFCS
             lo nibble  0 = 4/s · 1 = 10/s · 2 = 50/s · 3 = 1000/s · 4 = 10000/s (reserved)
  byte2 obj  ("5: 5*20 bytes")      byte3 crc8
reply: same 4-byte header + N × 20-byte queue records (§8.2)
  • Lifetime: streaming stops on USB disconnect or after 1 hour. Re-send 02 or 01 periodically to keep it running.
  • CRC-8 not identified: no standard CRC-8 reproduces both PDF examples (02 12 05→6A, 02 02 06→F2), and no CRC-8 table exists in any binary. Send the 1-byte form.

3.0.0 does not use this command. It uses the 0x15 frames in §3.2 instead. On CDC the meter therefore accepts at least three binary dialects: the docx 4-byte-header commands, the PDF's 1–4-byte "02" command, and the 0x15 frames.

11. Detected fast-charge protocol

Not found in 2.5.2 (Mtools or PDM):

  • There is no code→name table for the meter's on-screen "detected protocol".
  • The vendor list near Mt 0x140194… (Samsung, Apple, Huawei, Xiaomi, …) is a USB-IF VID→name table for PD Discover Identity.
  • PD_STATUS (0x020) is only hex-dumped (Mt FUN_14007a8d0 L64722–64731).
  • PDM detects protocols only via CDC entry …, which is state-changing.

3.0.0: also not found.

  • No protocol-name table, no entry commands, and no trigger UI.
  • The only candidate source of protocol state is the 0x15/08 reply (TypeCStateLog / PDStateLog / PDBuffer / ufcs_log TLVs). 3.0.0 never sends it (its timer is never started) and never decodes it.
  • The detected-protocol string therefore has to come from firmware analysis or experiments. Note that the 0x15/08 TLVs and the 2.5.2 PD_STATUS (0x020) block are the two device replies that might carry it, and neither PC app interprets them.

Upgrade on the wire (2.5.2 Mt FUN_14007afd0, capture updating_firmware):

  1. CONNECT.
  2. HEAD (reply u32@4 must be 0).
  3. 0x42 descriptor (64 B: model flag 0x4000, size, version, CRC, rand); expect ACCEPT.
  4. Send the ciphertext in 0xFF0-byte bulk writes, each answered with SYNC (0x01).
  5. Wait for FINISHED (0x07).

JUMP_DFU/APROM (0x09/0x08) switch between the bootloader and the application.

3.0.0 upgrade (Upgrade class) builds the 0x42 descriptor differently:

  • P3 FUN_1400dfe40 decrypts the image with key0 and takes the 64-byte info block at image offset 0x420 (the same layout as the device's 0x4420 block).
  • It checks that the block's model string matches the device.
  • It patches in size, CRC and a random word, and sends it as type 0x42 (L167492–167530).
  • Process states in the moc enum: Start, Erase, Dnload, Verify, VerifyFail, VerifyCorrect, Finished, TestJump, ReadInfo, ReadOpt, ReadQuid, ReadFlash1.

14. What the Go client must never send

  • Control types 0x04 RESET, 0x08 JUMP_APROM, 0x09 JUMP_DFU, 0x0A settings write (key 8 = factory reset), 0x0D GET_FILE.
  • Data types 0x42, 0x48, 0x4A, and raw 4080-byte firmware chunks.
  • HEAD as part of an upgrade, and the 2.5.2 auto-jump on a non-zero HEAD word.
  • 0x44 reads outside the five documented addresses.
  • 3.0.0 setOtpID / allocOtpID / jumpApp paths.
  • Every CDC text command (pdm …, entry …, reset, qc…, pd …, pd hrst, ufcs … …).

Safe set:

  • CONNECT, the 0x4C auth (mode 1), and 0x44 reads of the info/OTP/UID addresses.
  • GET_DATA with bits 0x001/0x002/0x008/0x010/0x040/0x200.
  • START/STOP_QUEUE and START/STOP_ANALYZER (sampling or sniffing only).
  • CDC 02/01/03.

Parse the ADC block by its sub-header size. Expect REJECT on START_QUEUE and recover the way the official app does.

Added by 3.0.0:

  • Type 0x43 OTP write (permanent device identity).
  • 0x15/05 with any attribute other than 0x32: unknown "set" semantics. 0x32 itself only starts/stops the stream.
  • Modbus RTU frames.

Safe 3.0.0 reads: 0x15/01, 0x15/02, 0x15/07, 0x15/08.

15. Method

  • Inputs: the official files listed in §2, identified by package-relative name and SHA-256. Downloaded files were treated as untrusted data and never executed.
  • Decompilation: a Ghidra 12.2 headless script decompiled every function of qt6_x64/POWER-Z.exe (3.0.0), Mtools.exe and PDM.exe (2.5.2), and listed string cross-references. radare2 was used for disassembly checks.
  • QML: recovered from the 3.0.0 executable's embedded Qt resources: 16 zlib-compressed files and 17 plain-text files. The rest exist only as qmlcache bytecode.
  • Helper scripts: small scripts parsed the .mencrypt QDataStream header, carved length-prefixed text resources, brute-forced CRC-8 parameters, and verified the AES keys and CRC-32 against captured traffic.
